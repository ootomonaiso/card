## 1. 前提条件

| # | 前提 |
|---|------|
| A1 | 実装者は1名（ハード・ソフト兼務）を想定 |
| A2 | 1人日 = 6時間（純作業。調査・休憩等を除く実働） |
| A3 | ハードウェア（Pi本体・タッチスクリーン・RC-S380・LE-53・部品）は手元にある前提 |
| A4 | 言語 Python、DB SQLite、GUI は既知のツールキットを使用 |

| A7 | 工数は中央値見積。楽観/悲観は第6章に併記 |

## 3. WBS（作業分解）と工数内訳

### ① ハードウェア・解錠制御（2.0人日）

| ID | 作業 | 対応要件 | 工数(h) |
|----|------|----------|:---:|
| HW-1 | LE-53 定格確認・駆動回路設計の確定（MOSFET/リレー＋還流ダイオード） | CON-1, NFR-08 | 2.0 |
| HW-2 | 駆動回路の組み立て（ブレッドボード→実装） | FR-05 | 3.0 |
| HW-3 | GPIO 解錠テスト（数秒通電→OFF、再施錠タイミング確認） | FR-05, NFR-08 | 3.0 |
| HW-4 | RC-S380 + nfcpy の IDm 読取確認・配線取り回し | FR-01 | 2.0 |
| HW-5 | Pi/ロック電源の分離検討・給電確認 | NFR-01 | 2.0 |

> LE-53 は **DC5V / 2W（≒0.4A）・通電時解錠型**（メーカー確認済み）。「数秒通電→OFF」で通電が切れた瞬間に施錠されるため、HW-3 で解錠保持時間の調整が要点。

## 5. 前提が崩れた場合の追加工数（リスク）

| 条件 | 追加工数(目安) | 根拠 |
|------|:---:|------|
| RC-S380 で社員証が読めない（方式差） | +1.0〜2.0 人日 | リーダー選定・再配線（[10] Q10） |
| LE-53 が「通電時施錠」型だった | +0.5 人日 | 解錠ロジック・停電時挙動の見直し（[09]） |
| ネットワークなし → RTC 追加 | +0.5 人日 | 部品調達・I2C実装（NFR-03） |
| 帳票と完全一致のCSV様式が必須 | +0.5 人日 | 列・書式・エンコード調整（[10] Q2） |
| 管理画面の要件が増える | +1.0 人日 | メンバー管理UIの作り込み（[10] Q3） |
| 延滞通知をフェーズ1に前倒し | +1.5 人日 | FR-10 相当（本来フェーズ2） |

## 7. 納期（11/11）との整合

- 既存スケジュール（[10] 第5章）は 11/5〜11/11 で、実装実働は概ね **6日**。
- 本見積の中央値は **約17人日**。1名・6時間/日では納期内に収まらない。
- 納期を維持する場合の選択肢：

| 選択肢 | 内容 |
|--------|------|
| スコープ縮小 | 初回は FR-01/02/03/04/05 + 最小CSV に絞り、メンバー管理(A02)・ログUI(A03)は簡易化／後日 |
| 増員 | ハード担当とソフト担当を分担（並行で実働短縮） |
| 稼働時間増 | 1日あたりの実働を増やす（品質・バッファとトレードオフ） |
| 納期見直し | 中央値17人日に合わせて日程を再設定 |

> 推奨：まず確認事項（[10] Q1〜Q10）を確定し、第5章の追加工数リスクを消す。そのうえで「初回納品スコープ」を上表のスコープ縮小案で合意するのが、納期と品質の両立に最も効く。
